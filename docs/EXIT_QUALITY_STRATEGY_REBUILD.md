# 出口品質の戦略立て直し (Exit Quality Strategy Rebuild)

**作成日**: 2026-09-19  
**対象フィクスチャ**: 西谷駅 → 居酒屋ウエチャベ (道玄坂2-9-2)  
**目的**: 出口品質の根本的な改善戦略を立案し、Preview環境での証明を経て段階的に実装する

---

## 1. 根本問題の枠組み

### 1.1 現状の挙動

deguchi-nabiの出口案内は以下の3層アーキテクチャで動作している：

```
[生成層: Gemini Search Grounding]
  ↓ 改札・出口テキストを生成
[判断層: JEV (TypeSafe System One)]
  ↓ retry判定・整合性チェック・完全性評価・候補選択
[プロダクト層: UI表示]
  ↓ confirmed/alternatives/unavailable の3状態
```

### 1.2 観測された問題

**本番環境での実績**:
- PR #129 (JEV Phase 2 A+B+C) マージ後
  - N=2: 両方とも「gate は OK だが exit が確認できません」
- PR #130 (selectFinalGuide + リトライ修正) Preview
  - N=5: 3件 OK、1件 exit欠損、1件タイムアウト
  - **出口ヒット率 ~60%**

### 1.3 根本原因の診断

#### 問題1: 生成層の不安定性

**症状**: Gemini Search Groundingが出口テキストを返さない、または検索結果に含まれない

**根本原因**:
1. **プロンプトの曖昧性**: 「改札・出口を確認」という指示が、検索クエリの生成と抽出の両方で解釈される余地がある
2. **検索クエリの不足**: Geminiが生成する検索クエリが、出口情報を含むページを見逃す可能性
3. **抽出の失敗**: 検索結果に出口情報があっても、抽出フェーズで見落とす
4. **情報源の限界**: Web上に該当する出口情報が存在しない、またはアクセスできない形式

**証拠**:
- PR #130の検証: JEV判断を厚くしても、Geminiが生成しないテキストは生まれない
- タイムアウト: 100秒という長いタイムアウトでも一部で発生
- 確率的な成功: 同じクエリでも成功率が60%程度

#### 問題2: 判断層の限界

**症状**: JEVが「gate-only confirmed」を検出してretryを指示するが、2回目も失敗する

**根本原因**:
1. **Retry期待の誤り**: JEVが「retryで改善する見込み」と判断しても、生成層の問題が確率的である場合、retryは単なる再試行でしかない
2. **フォールバックの脆弱性**: JEVが失敗した時のルールベース判定が保守的すぎる（confirmed partial → retry）

#### 問題3: プロダクト期待とのミスマッチ

**症状**: ユーザーは「出口が確認できません」より「おおよその方向」を望む

**根本原因**:
1. **3状態モデルの限界**: `unavailable` は情報がないことを示すが、方角情報があれば有用
2. **座標ベース選定との乖離**: 04_EXIT_SELECTION_DESIGN.mdで設計された座標ベース選定は、fixture駅では動作するが、AI生成駅では `coordinates: null` のまま
3. **閉世界仮定の誤り**: 候補集合が不完全な場合の対処（Phase 1.5で方角案内を導入）は機能しているが、そもそも候補がない場合には無力

## 2. オプションと tradeoff

### Option A: プロンプト精緻化 + 出口特化生成

**アプローチ**:
1. 現在の single-call (経路+改札+出口) を分割
   - 経路生成: 既存のまま
   - 改札・出口生成: **出口情報に特化した別プロンプト**で2回目の呼び出し
2. 出口プロンプトの強化:
   - 駅名 + 目的地座標を明示
   - 「出口名」「出口記号」「方角」の3つを必ず抽出するよう指示
   - 検索クエリのヒント（「駅名 出口 地図」など）を含める
3. 検索結果の複数候補処理
   - alternatives状態を積極的に活用
   - 2-3個の候補があれば、JEVで最適候補を選択 (Phase 2-B)

**長所**:
- 既存アーキテクチャ（Gemini + JEV）を活用
- 出口情報に注力することで、検索・抽出の精度向上を狙える
- 方角情報をフォールバックとして明示的に取得

**短所**:
- API呼び出しが増加（1回→2回）→ レイテンシ増加
- プロンプト改善は試行錯誤が必要 → 安定性の保証が難しい
- 根本的な情報源の限界（Web上に情報がない）は解決しない

**推定成功率**: 60% → 75-80%（仮説）

---

### Option B: データソース統合 (Fixture拡充 + OSM)

**アプローチ**:
1. Fixture駅の拡充
   - 主要駅（渋谷・新宿・横浜など）の出口を手動調査
   - 座標・connectedGateId を実データで整備
   - 04_EXIT_SELECTION_DESIGN.md の座標ベース選定を活用
2. OpenStreetMap (OSM) データの取り込み
   - `railway=subway_entrance` 等のタグで出口候補を取得
   - 座標と名称を自動取得
   - Confidence: medium (地図確認済み)
3. AI生成を補助役に限定
   - 候補URL探索、表記揺れ正規化、既存データとの照合のみ
   - 候補生成の一次ソースにはしない

**長所**:
- 高信頼データ（fixture）で主要駅をカバー → 安定性が高い
- OSMデータで全国カバレッジを拡大 → スケーラビリティ
- AI依存度を下げる → 予測可能性が向上

**短所**:
- 初期投資が大きい（fixture整備、OSM統合の実装）
- OSMの網羅性に依存 → 日本の地下街接続などは不完全
- リアルタイム性が低い（fixture/OSMの更新サイクル）

**推定成功率**: 主要駅 95%+、全国 70-80%（OSM網羅性次第）

---

### Option C: プロダクトUXの再定義 (approximate tierの拡充)

**アプローチ**:
1. 3状態モデルの拡張
   - `confirmed` (断定): 具体的な出口名
   - `approximate` (方角): 「◯◯側の出口をご利用ください」
   - `unavailable` (不明): 「確認できません」
2. 方角案内の優先
   - 駅座標と目的地座標から方角を計算（既存の bearing.ts を活用）
   - 候補がない、または候補の信頼度が低い場合、方角案内を表示
3. 段階的情報開示
   - 「詳細な出口情報を取得中...」といった進行表示
   - 出口が確定しなくても、経路・改札は先に表示

**長所**:
- 実装コストが低い（既存のロジックを活用）
- ユーザー体験の改善 → 「確認できません」より方角のほうが有用
- 04_EXIT_SELECTION_DESIGN.md の Phase 1.5 (閉世界仮定対処) と一貫

**短所**:
- 根本的な出口名の安定化にはならない
- 「方角だけ」はユーザー期待に応えられない可能性
- 信頼度の低い出口名を出すより安全だが、理想的ではない

**推定成功率**: 方角案内 95%+、具体的出口名は現状維持（60%）

---

### Option D: アーキテクチャ分割 (二段階ストリーミング拡張)

**アプローチ**:
1. PR #128 の二段階ストリーミングを拡張
   - First stream: 経路のみ（高速表示）
   - Second stream: 改札・出口（時間をかけて精緻化）
2. 出口生成の複数試行
   - 2回の生成を並列実行（Promise.all）
   - 両方の結果を統合（JEV Phase 2-B で候補選択）
3. タイムアウトの段階的短縮
   - 1回目: 30秒（高速レスポンス）
   - 2回目: 60秒（精度重視）
   - 両方失敗時: 方角案内にフォールバック

**長所**:
- ユーザー体感レイテンシを改善（経路は早く表示）
- 複数試行で成功率を向上 → 60% × 2回 → 84%（独立試行仮定）
- 既存の二段階ストリーミング基盤を活用

**短所**:
- 実装複雑度が増加（並列実行、結果統合）
- API呼び出しコスト増加（2倍）
- タイムアウトの調整が難しい（短すぎると失敗、長すぎると遅延）

**推定成功率**: 60% → 84%（理論値、2回独立試行の場合）

---

## 3. 推奨パスの選択（証拠付き）

### 3.1 短期推奨: **Option A (プロンプト精緻化) + Option C (approximate tierの拡充)**

**理由**:
1. **実装コストが低い**: 既存のアーキテクチャを活用し、プロンプトとUXの改善に集中
2. **段階的展開が可能**: Previewで検証してから本番投入
3. **リスクが低い**: 既存の二段階ストリーミング（#128）とJEV統合（#129）を保持
4. **ユーザー体験の即時改善**: 方角案内により「確認できません」を減らす

**証拠**:
- PR #130の教訓: JEV判断を厚くするだけでは不十分 → 生成層の改善が必要
- 04_EXIT_SELECTION_DESIGN.md Phase 1.5: 方角案内は既に設計・実装済み → 拡充は自然
- PR #128の成功: 二段階ストリーミングで体感遅延を改善 → 保持すべき

**実装計画**:
1. **Phase 1: プロンプト精緻化** (1-2日)
   - single-call-navigator.ts のプロンプトを分割
   - 出口専用プロンプトの作成（方角抽出を必須化）
   - Preview N=10で検証 → 目標: 出口ヒット率 75%+
2. **Phase 2: approximate tierの拡充** (1日)
   - bearing.ts を使って方角を計算
   - facility.state に `approximate` を追加（または既存の alternatives を活用）
   - UI: 「◯◯側の出口をご利用ください」を表示
3. **Phase 3: 統合テスト** (1日)
   - 西谷→ウエチャベで N=20 テスト
   - 目標: 出口（具体名 or 方角） ヒット率 90%+
   - 本番デプロイ

---

### 3.2 中期推奨: **Option B (Fixture拡充 + OSM統合)**

**理由**:
1. **高信頼データで安定性を確保**: 主要駅は fixture で 95%+ の精度
2. **全国カバレッジの拡大**: OSMデータで長尾をカバー
3. **AI依存度を下げる**: 予測可能性と保守性の向上

**実装計画**:
1. **Phase 4: Fixture拡充** (1週間)
   - 主要10駅（渋谷、新宿、横浜、東京、品川、池袋、大阪、名古屋、福岡、札幌）
   - 各駅3-5出口を調査・登録
   - 座標・connectedGateId を整備
2. **Phase 5: OSM統合** (2週間)
   - OSM Overpass API で `railway=subway_entrance` を取得
   - StationFacility への変換ロジック
   - Confidence: medium で登録
3. **Phase 6: AI補助役への降格** (1週間)
   - AI生成は fixture/OSM に候補がない場合のみ
   - 生成結果は Confidence: low で扱う
   - UI: low は方角案内のみ表示

## 5. 段階的計画と成功指標

### 5.1 Phase 1+2（統合）: プロンプト精緻化 + 方角フォールバック（短期）

**目標**: 出口生成の精度向上 + 方角フォールバック

**背景（アーキテクチャレビュー指摘）**:
- Phase 1とPhase 2は技術的に密結合（出口抽出時に方角も同時に取得すべき）
- 分割すると、2段階の検証が必要になり工数が増加
- 統合実装により、PR #130の修正（fail-open、partial→full検出）を新設計で置き換える

**タスク**:
1. **プロンプト精緻化**
   - single-call-navigator.ts のプロンプトを改善（分割不要、既存プロンプトの強化で対応）
   - 出口情報の抽出強化:
     - 「出口名」「出口記号」「方角（北/南/東/西/北東/北西/南東/南西）」を必ず抽出
     - facilityCandidates の reason フィールドを充実（「目的地は◯◯側」等）
   - 検索クエリヒント: 「{駅名} 出口 地図 {目的地方向}」を明示
2. **抽出スキーマの拡張**
   - `RawFacilityCandidate` に `exitDirection: string | null` を追加
   - `facilityCandidates` の `reason` を必須化（null許容だが優先的に埋める）
3. **方角フォールバックの実装**
   - bearing.ts を使って駅→目的地の方角を計算
   - 出口名が取得できない場合、方角を directionHint として保存
   - FacilityRecommendation に方角情報を追加: `directionHint: string | null`
4. **UI実装**
   - confirmed: 「◯◯改札、◯◯出口」
   - approximate: 「◯◯改札、◯◯側の出口」（方角のみ）
   - unavailable: 「確認できません」（方角も取れない場合、まれ）
5. **selectFinalGuide の改善**
   - partial (gate-only) → full (gate+exit) の改善を検出
   - PR #130 の facilityScore ロジックを簡略化して統合
6. **Preview N=10 テスト**
   - フィクスチャ: 西谷 → ウエチャベ
   - 成功指標: 出口名 or 方角のヒット率 80%+

**成功基準**:
- 出口情報（具体名 or 方角）ヒット率: 80%+ (N=10)
- タイムアウト率: 10%以下（現状: 100秒で約5%発生）
- **3段階の成功率測定**（アーキテクチャレビュー指摘）:
  - **取得率**: Geminiが出口情報（名前 or 方角）を返した割合
  - **確定率**: confirmed または approximate に分類できた割合
  - **正確率**: ユーザー検証で正しかった割合（手動確認）

**コスト監視指標**（Thermosレビュー指摘）:
- Preview N=10での1クエリあたりAPI呼び出しコスト測定
- 許容閾値: 現状の150%以内（具体値は実測後設定）
- 超過時の対処: プロンプト短縮またはキャッシュ実装

**ロールバック戦略**（Thermosレビュー指摘）:
- Phase 1+2実装が成功基準(80%)未達の場合:
  1. feature branchを本番マージせず放置
  2. 既存#128/#129の動作を維持
  3. Option Bへの移行判断を実施
- 本番マージ後に問題が発覚した場合:
  1. 即座にrevert PR作成
  2. Preview環境で再検証

## 6. 明示的な非目標

以下は**今回の計画では実施しない**:

1. **盲目的なリトライの追加**
   - JEV Phase 2-Cの完全性評価によるretryは、生成層の確率的失敗を解決しない
   - 代わりに、生成層の精度向上と方角フォールバックで対処

2. **PR #130 のマージまたは追加パッチ**
   - 根本問題を解決しないため、新戦略で置き換える
   - Draft 放置または Close を推奨

3. **「Phase N complete」言語の使用**
   - 誤解を招く進捗表現を避ける
   - 代わりに「出口名ヒット率 75%」のような定量的指標を使う

4. **Fail-open の破壊**
   - JEV失敗時にサーチ全体が壊れてはいけない
   - すべての改善は、JEV無効時でも動作する設計を維持

5. **Preview なしでの本番マージ**
   - すべての出口「修正」は、Preview N=10+ で証明してからマージ

6. **Geminiの置き換え**
   - Gemini Search Grounding は長文生成に継続使用
   - JEVは判断スライスのみ（選択・完全性・一貫性・リトライ）

---

## 7. リスクと緩和策

### 7.1 リスク: プロンプト改善が期待通りの効果を出さない

**緩和策**:
- Preview で N=10 テストを必須化
- 目標（75%+）に達しない場合、Option B (Fixture拡充) に切り替え

### 7.2 リスク: 方角案内がユーザー期待を満たさない

**緩和策**:
- フィードバック機能で「方角案内は役立ちましたか？」を収集
- 否定的フィードバックが多い場合、Fixture拡充を優先

### 7.3 リスク: API呼び出しコストの増加

**緩和策**:
- プロンプト分割による呼び出し増加を監視
- コストが許容範囲を超える場合、キャッシュ戦略を追加

### 7.4 リスク: タイムアウト率の増加

**緩和策**:
- タイムアウトを段階的に設定（1回目 30秒、2回目 60秒）
- タイムアウト時は方角案内にフォールバック

### 7.5 リスク: JEV依存度の増加（アーキテクチャレビュー指摘）

**緩和策**:
- JEVのfail-open設計を維持
- JEV失敗時のルールベース判定を保持
- JEV疎通確認エンドポイント（#125）を活用

### 7.6 リスク: 方角案内の精度（アーキテクチャレビュー指摘）

**緩和策**:
- bearing.ts の計算ロジックを検証
- 駅座標の精度を確認（fixtureは高精度、AI生成は低精度）
- 方角は8方位（N/NE/E/SE/S/SW/W/NW）で表現

**方角案内の前提条件**（Thermosレビュー指摘）:
- 駅座標が取得できない場合: unavailable状態にフォールバック
- Phase 4(Fixture拡充)以降は、主要10駅で座標精度を保証
- AI生成駅で `coordinates: null` の場合、方角計算は不可能（unavailableへフォールバック）

## 付録: 用語集
