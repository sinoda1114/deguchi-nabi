## 1. PR #132 失敗理由の証拠

### 1.1 診断結果サマリー

pstack診断により、4層の問題を特定した：

| 層 | 問題 | 寄与度 | 改善可能性 |
|---|---|---|---|
| **製品スコープ** | gate AND exit 必須の厳格化、方角フォールバック無効化 | **40-50%** | **高** |
| **生成層** | Gemini出口名抽出の構造的限界 | **30-40%** | 低 |
| **インフラ層** | retry頻度増加、タイムアウト多発 | **20-30%** | 中 |
| **判定層** | JEV Phase 2-C の過剰retry判定 | **10-15%** | 中 |

### 1.2 最も重要な実装ミス

**方角フォールバックが無効化されていた**:

```typescript
// classifyFacilityRecommendation で gate-only を除外
const validPairs = dedupePairs(pairs.filter((pair) => 
  pair.gate !== null && pair.exit !== null  // ← gate-only を除外
));

// toGuide 内の方角フォールバック条件
if (
  facility.state === "confirmed" &&
  facility.pair.gate !== null &&  // ← この条件に到達できない
  facility.pair.exit === null &&
  context.destinationCoordinates
)
```

**結果**: gate-only結果は `classifyFacilityRecommendation` の段階で除外されるため、方角フォールバックの条件に到達しない。

### 1.3 なぜプロンプト改善だけでは不十分だったか

**生成層の構造的限界**:

1. **検索結果に出口名が含まれない**
   - 駅構内図: PDF/画像形式が多く、テキスト検索でヒットしない
   - Google Maps: 出口名が記号的（「A2」「東口」）で、目的地との対応関係が不明
   - 個人ブログ: 出口名を省略（「駅を出たら右折」など）

2. **exitDirection の抽出成功率も60%**
   - exitDirection を必須化したが、実測で60%しか成功していない
   - 方角情報も検索結果に含まれないケースが多い

3. **Geminiの制約**
   - 「創作禁止」「逐語一致のみ」の制約下で動作
   - 検索結果に含まれない情報は推測で補完できない

**結論**: プロンプト改善だけでは、検索結果に情報がなければ抽出できない。データソースの追加（OSM統合、Fixture拡充）が必要。

## 2. 正直な診断

### 2.1 生成層（Gemini Search Grounding）

**問題**: 出口名の抽出精度が構造的に低い（40-50%）

**根本原因**:
- 検索結果に出口名が含まれない（構内図PDF、情報省略）
- プロンプト改善の限界（情報がなければ抽出できない）

**寄与度**: 30-40%

**対策**:
- 短期: プロンプト最適化（Option I）で+2-3%の改善
- 中期: OSM統合（Option C）で出口座標データを補完
- 長期: Vision統合（Option H）で構内図画像を直接解析

### 2.2 判定層（JEV判定）

**問題**: retry判定が過剰で、タイムアウトリスクを増幅

**根本原因**:
- Phase 2-C が不完全結果をretryループに戻す
- JEVタイムアウト1秒（短すぎる）
- retry頻度40%（以前は10-15%）

**寄与度**: 10-15%

**対策**:
- 短期: Phase 2-C スキップ（Option F）
- 短期: JEVタイムアウト延長（Option G）
- 中期: retry判定を保守的に（approximate状態はretryしない）

### 2.3 製品スコープ（UX期待 vs 実装）

**問題**: gate AND exit 必須の厳格化で、方角フォールバックが無効化

**根本原因**:
- gate-only結果を失敗扱い
- 方角フォールバックの適用条件に到達不可能
- ユーザー期待とのミスマッチ（gate + 方角でも有用）

**寄与度**: 40-50%（最も支配的）

**対策**:
- 短期: gate-only成功化（Option A）で方角フォールバック有効化
- 短期: 部分的UX（Option E）でgate案内のみでも価値提供

### 2.4 インフラ層（タイムアウト、レイテンシ）

**問題**: retry頻度増加とGeminiレイテンシ変動でタイムアウト率30%

**根本原因**:
- retry頻度40%（以前は10-15%）
- Geminiレイテンシ変動（38.9〜75.6秒）
- 2回試行で230秒 → タイムアウト

**寄与度**: 20-30%

**対策**:
- 短期: retry頻度削減（Option F）で大幅改善
- 中期: 予算管理最適化

### 3.2 主要オプションの詳細

## 7. 明示的な非ゴール

以下は**今回の計画では実施しない**:

1. **Option B（別々の gate/exit 生成）**
   - 理由: レイテンシ2倍、コスト2倍で、Option Aと同等の効果
   - 代替: Option Aで低コスト・低リスクに達成

2. **Option J（アーキテクチャ分割）**
   - 理由: 複雑性大、保守コスト高で、Option A+Eと同等の効果
   - 代替: Option A+Eで低コスト・低リスクに達成

3. **Option H（Vision統合）**
   - 理由: コスト2-3倍、レイテンシ増加、Phase 2で目標達成済み
   - 将来検討: 90%+を目指す場合のみ（Phase 3以降）

4. **盲目的なリトライ追加**
   - 理由: タイムアウトリスク増、retry成功率が低い
   - 代替: retry判定を保守的に（Phase 0, 1）

5. **Gemini の置き換え**
   - 理由: 他の生成AIも同様の構造的限界がある
   - 代替: データソース追加（OSM統合、Fixture拡充）

6. **fail-open の破壊**
   - 理由: システムの堅牢性を損なう
   - 保持: JEVタイムアウト時のルールベースフォールバック

7. **Preview なしでの本番マージ**
   - 理由: 目標未達のリスク
   - 必須: 各Phase で Preview N=10-20 測定後にマージ

8. **「Phase N complete」表現の使用**
   - 理由: 誤解を招く（ユーザーはフェーズを理解していない）
   - 代替: 具体的な改善内容を説明

## 9. ロールバック戦略

### 9.1 Phase 0

**ロールバック条件**（数値化）:
- BothHit率が現状（60%）より低下（実測値<55%）
- タイムアウト率が現状（30%）より悪化（実測値>35%）
- 平均レイテンシが120秒を超過

**ロールバック手順**:
1. main から該当コミットをrevert
2. 原因調査（N=10での詳細ログ分析）
3. 修正版を Preview で再検証（N=30）後に再マージ

**ロールバック判断タイミング**:
- N=10で明らかな失敗（BothHit<55%）なら即座にロールバック
- N=30で目標未達（BothHit<65%）なら原因調査後にロールバック

### 9.2 Phase 1

**ロールバック条件**（数値化）:
- N=30でBothHit率<75%（信頼区間下限<65%）
- タイムアウト率>15%
- ユーザーフィードバックで「出口名が欲しかった」が30%超

**ロールバック手順**:
1. main から Phase 1 のコミットをrevert
2. Phase 0 の状態に戻す
3. 失敗要因分析（Option Aの実装ミスか、前提の誤りか）
4. 代替案（Option C単体など）を検討

**ロールバック判断タイミング**:
- N=10で明らかな失敗（BothHit<70%）なら即座にロールバック
- N=30で目標未達（BothHit<75%）なら原因調査後にロールバック

### 9.3 Phase 2

**ロールバック条件**（数値化）:
- N=50でBothHit率<82%（信頼区間下限<72%）
- OSM APIの制限・障害でデータ取得成功率<80%
- 正確性<75%（信頼区間下限<65%）

**ロールバック手順**:
1. main から Phase 2 のコミットをrevert
2. Phase 1 の状態に戻す
3. 失敗要因分析（OSM統合の問題か、Fixtureデータの品質か）
4. Option D（Fixture拡充）単体に切り替え、またはPhase 1で運用継続

**ロールバック判断タイミング**:
- OSM APIが利用不可なら即座にロールバック（Option D単体に切り替え）
- N=50で目標未達（BothHit<82%）なら原因調査後にロールバック
